Here’s a tight, scalable MySQL naming convention you can adopt as a team standard. It’s opinionated, proven, and easy to lint.

Core rules

Case & style: lower_snake_case everywhere (databases, tables, columns, indexes, constraints, views, routines).

Language: English, full words > cryptic abbreviations (amount not amt).

Singular vs plural: Tables are singular (user, order, invoice_item). Junction tables are also singular but alphabetically ordered: order_user, permission_role.

Prefixes: Avoid type or project prefixes (tbl_, col_, myproj_). They add noise without value.

Reserved words: Never use MySQL reserved words; if you must, suffix/prefix (e.g., order_number not order).

Databases

Name by product and bounded context: acme_billing, acme_analytics.

For environments: acme_billing_dev, acme_billing_stg, acme_billing_prod (or separate servers; just be consistent).

Tables

Primary key: id BIGINT UNSIGNED AUTO_INCREMENT (or BIGINT surrogate when using UUIDs elsewhere).

FK columns: <referenced_table_singular>_id (e.g., user_id, currency_id).

Timestamps: created_at, updated_at, optional soft-delete deleted_at (NULL when active). Store UTC.

Booleans: is_active, is_default, has_trial (avoid bare adjectives).

Amounts & units: suffix with unit or type: price_cents, weight_kg, duration_ms.

JSON columns: suffix _json (e.g., metadata_json) and document shape in code/docs.

Enums: Prefer lookup tables (status table) unless state list is tiny and immutable; if using ENUM, name like order_status and still keep a mapping in code.

History/audit: Suffix _hist for immutable history, _log for append-only logs, _bk for short-term backups (time-boxed).

Partitions/shards: Keep base name stable; suffix physical partitions if truly separate tables: event_2025q3, but prefer native partitioning.

Constraints & indexes

Use consistent, descriptive names. Suggested patterns:

Primary keys: pk_<table> → pk_user

Foreign keys: fk_<table>__<column>__<ref_table> → fk_order__user_id__user

Unique keys: ux_<table>__<col1>[_<col2>] → ux_user__email

Non-unique indexes: ix_<table>__<col1>[_<col2>] → ix_order__created_at, ix_order__user_id_created_at

Check constraints (MySQL 8.0+): ck_<table>__<rule> → ck_invoice__amount_cents_nonneg

Fulltext indexes: ft_<table>__<col> → ft_article__content

Views, routines & triggers

Views (read models): v_<purpose> → v_user_last_login

Stored procedures (if used): sp_<action>_<noun> → sp_rebuild_materialized_views

Functions: fn_<what> → fn_normalize_phone

Triggers: trg_<table>__<timing>_<event> → trg_order__before_insert

Migrations

Files: YYYYMMDDHHMMSS__<action>_<object>.sql → 20250928_103012__add_ux_user__email.sql

One object/action per file where practical.

Additional conventions that pay off at scale

Character set/collation: default to utf8mb4 and a modern collation (e.g., utf8mb4_0900_ai_ci). Override per-column when you need case sensitivity (_as_cs).

Time: store in UTC (DATETIME(6) or TIMESTAMP where semantics fit). Name columns with _at.

Length & types: pick explicit types with rationale; avoid TEXT/BLOB unless necessary. Keep varchars sized (e.g., email up to 320).

Nullable: default to NOT NULL; make nullability explicit and meaningful.

IDs: if you need external-safe IDs, add public_id (UUIDv7/ULID) with unique index; keep id as surrogate PK for joins.

Naming collisions: if a table would collide with a reserved word, extend the noun (order is OK, but e.g., use group_account not group).

API alignment: prefer DB names that mirror API fields; avoid translation layers of synonyms.

Archival: suffix _archive for cold storage tables with the same schema; write-only except maintenance.

Temporary tables: tmp_<purpose>_<short_id> for session/workflow temps; don’t check into migrations.

Consistency first: if you must break a rule, document it in a short README next to migrations.

🚀 MySQL Naming Conventions & Schema Standards for Scalable Projects

Designing databases for small projects often feels straightforward—just pick names that “make sense” and move on. But as projects grow—across teams, environments, and years—the cost of inconsistent naming balloons. Queries become harder to debug, migrations risk collisions, and APIs drift away from the data layer.

This article lays out a comprehensive MySQL naming convention and schema standard that is:

Scalable (works for hundreds of tables and billions of rows)

Consistent (minimizes ambiguity and debate)

Practical (fits real-world engineering workflows)

Lintable (rules can be enforced automatically in CI/CD)

1. Core Rules
Lowercase Snake Case

Rule: Use lower_snake_case for all identifiers.

Why: Consistency across tables, columns, and indexes makes queries predictable and easy to write without quoting. MySQL is case-insensitive on some systems, so camelCase or PascalCase introduces portability issues.

✅ Example:

user_account, created_at, ix_order__created_at


❌ Anti-patterns:

UserAccount, CreatedAt, ixOrderCreatedAt

English, Full Words

Rule: Prefer full English words over abbreviations.

Why: Shortened forms like amt or ctry save a few keystrokes but create cognitive load. Database schemas should prioritize clarity over brevity.

✅ amount, country_code
❌ amt, ctry_cd

Singular Table Names

Rule: Use singular nouns for tables: user, order, invoice_item.

Why: Tables represent a set of entities; the name should reflect the entity type, not the collection. This also avoids pluralization inconsistencies in English (e.g., person vs people).

✅ user, order
❌ users, orders

For junction tables, use singular + alphabetical order:
✅ order_user
❌ user_order

No Prefixes

Rule: Avoid prefixes like tbl_, col_, or myproj_.

Why: These don’t add information—MySQL already distinguishes tables from columns. Prefixes clutter queries and slow down autocomplete.

✅ invoice_item
❌ tbl_invoice_item

Avoid Reserved Words

Rule: Don’t name tables/columns after MySQL reserved words (order, group, select, etc.).

Why: Quoting them (\order``) leads to subtle bugs and makes SQL harder to read.

✅ order_number, group_account
❌ order, group

2. Database Naming

Rule: Use product + bounded context.

Why: Large organizations run multiple products and services. Names like acme_billing or acme_analytics clarify ownership.

✅ acme_billing, acme_analytics

For environments:
✅ acme_billing_dev, acme_billing_stg, acme_billing_prod

3. Tables & Columns
Primary Keys

Rule: Always use a surrogate id (BIGINT UNSIGNED AUTO_INCREMENT or UUID).

Why: Natural keys (like emails) can change, break foreign keys, and complicate joins.

✅

id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT PRIMARY KEY

Foreign Keys

Rule: <referenced_table>_id

Why: Explicit, predictable, and grep-able.

Rule: Always include created_at, updated_at; optionally deleted_at.

Rule: Prefix with is_ or has_.

Why: Boolean fields should read naturally in queries.

Rule: Append unit or base.

4. Constraints & Indexes

Primary key: pk_<table> → pk_user

Foreign key: fk_<table>__<column>__<ref_table> → fk_order__user_id__user

Index: ix_<table>__<col> → ix_order__user_id_created_at

Check (MySQL 8+): ck_<table>__<rule> → ck_invoice__amount_cents_nonneg

Fulltext: ft_<table>__<col> → ft_article__content

This makes debugging constraints trivial—names tell you exactly what failed.

5. Views, Routines & Triggers

Views: v_<purpose> → v_user_last_login

Stored procs: sp_<action>_<noun> → sp_rebuild_materialized_views

Functions: fn_<purpose> → fn_normalize_phone

Triggers: trg_<table>__<timing>_<event> → trg_order__before_insert

Why: Avoids clutter in namespaces, keeps names meaningful and sortable.

6. Migrations

Rule: YYYYMMDDHHMMSS__<action>_<object>.sql

Why: Sorted by timestamp; makes rollbacks & CI runs predictable.

✅ 20250928_103012__add_ux_user__email.sql
❌ final_migration.sql

One action/object per file. Small, atomic, reversible.

7. Additional Conventions

Charset & Collation: Always utf8mb4 (full Unicode) + utf8mb4_0900_ai_ci (modern, case-insensitive).

Time: Always UTC, suffix with _at.

Types: Explicit sizes (VARCHAR(320))—avoid unbounded TEXT/BLOB.

Nullability: Default NOT NULL. Use NULL only if truly optional.

External IDs: Add public_id (UUIDv7/ULID) alongside surrogate id.

Archival: _archive tables for cold storage.

Temporary tables: tmp_<purpose>_<shortid>.

TL;DR recommendation

Use DB defaults for infrastructure/metadata fields that must always be valid regardless of how the row was created:
created_at (UTC clock), updated_at auto-touch, booleans that have a safe invariant (is_active), soft delete (deleted_at = NULL), “empty but valid” JSON ('{}'), etc.

Avoid DB defaults for business semantics that the application should decide: tenant, currency, locale, status transitions, quantities, pricing, user/actor fields, etc.

Never use “magic” defaults like empty strings '', zero-dates, or 0 sentinels to mean “unknown”. Use NULL + constraints/checks instead.

Prefer NOT NULL + explicit defaults where a value is truly required and has a safe invariant; otherwise NULL and let the app supply it.

Keep the source of truth consistent: if the database sets something automatically (e.g., updated_at), let it do so everywhere; don’t sometimes override from the app.

Why not “application-only defaults” for everything?

Relying purely on the application to set every default works until it doesn’t:

Multiple writers: admin consoles, background jobs, migration scripts, bulk imports, hand-made SQL, CDC replays… not all paths run the same app code. DB-side defaults keep data valid across all writers.

Operational safety: during incidents or partial deploys, DB defaults provide guardrails (e.g., timestamps) without relying on app availability or version consistency.

Auditability & reproducibility: DB-generated values (timestamps, ON UPDATE) are uniform and harder to spoof.

Developer ergonomics: fewer “cannot insert NULL…” surprises in ad-hoc maintenance.

But DB defaults can be harmful when they encode business choices (e.g., default currency 'USD' or default status = 'pending' when some flows require 'draft'). That’s how you get invisible bugs: code paths pass nothing and silently pick up the wrong default.

Defaults: Database vs Application — Decision Rules

Use DB defaults when ALL are true:

The default is environment-agnostic and timeless (will not change by tenant, region, or future product policy).

The default is structural/operational, not business behavior.

The value should be present for every row regardless of writer.

Examples to default in the DB

-- Timestamps (operational truth, UTC)

Avoid DB defaults when ANY are true:

The value encodes business logic or context (tenant, region, product state).

The correct default could change or depend on input.

You want mistakes to fail loudly (e.g., missing tenant_id should error).

Empty strings for “no value”

Empty string is a value, not “unknown”. It hides bugs and breaks uniqueness assumptions.

Zero dates / zero numbers as “unknown”

-- ❌ Don’t do this
due_date DATE NOT NULL DEFAULT '0000-00-00';


These poison comparisons and reporting. Use NULL and add checks where needed.

Magic business defaults

-- ❌ Don’t do this
currency_id SMALLINT UNSIGNED NOT NULL DEFAULT 840; -- assumes USD


Tenants/regions vary. This will silently corrupt data.

Dual sources of truth
If the DB auto-updates updated_at, do not sometimes set it from the app. Pick one owner.

SQL modes: run with strict modes so bad data can’t sneak in (e.g., no zero-dates).

NOT NULL: if a column is required and has a safe invariant, use NOT NULL + DB default; else use NOT NULL without a default to force app supply (and fail fast).

Generated columns: if a default is actually a derivation, use a generated column instead of baking a default that can drift.

Triggers vs app logic: for purely mechanical fields (updated_at), DB is a good owner; for anything businessy, keep it in the app service layer.

The idea you’re proposing

Business semantics: things like status, tenant_id, due_at, published_at, cancelled_at.

Multiple writers & tools

Operational incidents

Auditability & trust

Data quality over time

Enforce NOT NULL for created_at/updated_at so writers must provide them.
